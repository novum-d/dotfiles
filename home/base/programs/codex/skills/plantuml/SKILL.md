# PlantUMLの図を扱う

読み手が構造や流れを短時間で理解でき、ローカルCLIで再現可能なPlantUMLソースを作る。

## 作業方針

- 既存の図を扱う場合は、先に周辺のPlantUMLファイル、include、テーマ、命名、出力方法を確認し、必要な箇所だけを変更する。
- ユーザーが図の種類や出力形式を指定している場合は、その選択を維持する。
- 指定がない場合は、時系列のやり取りにはシーケンス図、処理と分岐にはアクティビティ図、状態遷移には状態図、型と関係にはクラス図、ソフトウェア構成にはコンポーネント図、実行環境の配置には配置図を選ぶ。
- 1枚に情報を詰め込みすぎず、主題から外れる詳細は省くか、図を分ける。
- 表示名と参照用aliasを分離し、関係線では短く安定したaliasを使う。既存図にない配置指定や装飾は、理解を明確に改善する場合だけ追加する。
- 新規の通常図は `@startuml` と `@enduml` で囲み、リポジトリで別の規約がなければ `.puml` を使う。

## 内容の正確性

- 図にする対象がコードや構成ファイルに存在する場合は、実物を確認してから要素、方向、依存関係、呼び出し順を記述する。
- 観測できた事実と、簡略化した表現や推定を混同しない。重要な省略や仮定は図中のnoteまたは説明で明示する。
- シーケンス図では、呼び出しと応答、同期と非同期、条件分岐、並行処理を区別する。
- アーキテクチャ図では、論理コンポーネント、プロセス、ホスト、外部サービスの階層を混同しない。
- 要素名、ラベル、noteはユーザーの言語に合わせ、コード上の識別子や正式名称は原表記を保つ。

## 検証と出力

1. `plantuml` が利用可能か確認する。リポジトリ固有の検証コマンドがあればそれを優先する。
2. CLIの世代差が疑われる場合は `plantuml -help` または `plantuml --help` で、その環境が対応するオプションを確認する。
3. 対応している場合は `plantuml --check-syntax <file>`、旧CLIでは `plantuml -checkonly <file>` を使って構文を検証する。
4. レイアウトも成果物の一部なら、一時ディレクトリへPNGまたはSVGを生成し、切れ、重なり、読みにくい交差、過度な横幅がないか確認する。生成物を依頼された場合だけ、指定された場所へ保存する。
5. 検証できなかった場合は、未検証の範囲と理由を明記する。

構文が通っても、関係の方向や説明の正しさまでは保証されない。必ず元資料との対応も確認する。

## includeと安全性

- 実行前に `!include`、`!include_many`、`!includeurl`、外部spriteやテーマの参照を確認する。
- 信頼できないPlantUMLソースは、ローカルファイルやネットワークへアクセスできない `PLANTUML_SECURITY_PROFILE=SANDBOX` で検証・生成する。必要なincludeがある場合は、ユーザーが指定した信頼済みの範囲だけを許可する。
- 非公開情報を含む図を公開PlantUMLサーバーへ送信しない。ローカルCLIを優先する。
- リモートincludeを新たに追加する場合は、再現性と可用性への影響を説明し、可能ならリポジトリ管理のローカル資材を使う。

## 完了時の報告

作成・変更したソースと、実行した構文検証またはレンダリング結果を簡潔に伝える。図を簡略化した場合は、重要な省略だけを併記する。
